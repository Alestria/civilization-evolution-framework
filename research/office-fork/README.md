# 组织分叉后多维连接的异步演化——以 OpenOffice 与 LibreOffice 为例

*Asynchronous Evolution of Multidimensional Connectivity Following Organizational Forking: A Case Study of OpenOffice and LibreOffice*

**第一阶段档案研究 · 2010—2015 年**

LibreOffice 在 2010 年分叉后，与后来进入 Apache 的 OpenOffice 沿各自的治理路径发展。2012—2015 年抽取的四组近同期版本都保留了 Writer 的 ODT 读写入口。2014 年有涉及两项目的修订记录互操作演示，2015 年一位 Apache OpenOffice 用户确认打开了由 LibreOffice 生成的一份 ODT。这些记录说明，治理分开后，具体的文档接口仍能继续使用。两条路径间的 Writer 维护协作和成员认同如何变化，现有档案还无法判定。[时间线、配置原档与运行记录](evidence.md)

## 研究问题与范围

组织分叉以后，原先连在一起的技术接口、工作关系、制度安排和成员归属，会不会在同一时间变化？本研究以 2010 年 9 月 28 日公布 LibreOffice 项目为时间锚，追踪至 2015 年底。组织材料区分三段：分叉前的 OpenOffice.org、LibreOffice 发起后仍独立存在的 OpenOffice.org，以及此后由 Apache 治理的 Apache OpenOffice。技术比较收窄到 Writer 的 ODT 读写，软件发布、配置、实际文档交换和维护协作分别取证。

Gamalielsson 与 Lundell（2014）已经研究了这一分叉的治理背景、版本库活动、贡献者留存和跨项目参与，版本库观察大体截至 2013 年 5 月。本文借用这一基线，把单位改为具体发布版本、一次文档交换或同一维护事项。2013 年 LibreOffice 大会上也已有跨软件互操作测试，现阶段只能说明本文的观察范围，原创性仍待进一步检索。[同行研究](https://doi.org/10.1016/j.jss.2013.11.1077) · [2013 年互操作测试报告摘要](https://conference.libreoffice.org/2013/en/program/open-document-format/a-multiplatform-tool-for-document-interoperability-testing.html)

## 观察结果

| 维度 | 档案所见 | 结论边界 |
| --- | --- | --- |
| 治理与制度安排 | LibreOffice 发起独立项目。Apache 接收 OpenOffice.org 源码，随后建立项目管理委员会。文档基金会于 2012 年在柏林正式成立。 | 两条治理路径可分别确认。机构公告中的接触意向只记录为意向。 |
| 许可证 | Apache OpenOffice 3.4 公告采用 Apache License 2.0。LibreOffice 4.1 的 Writer 类型文件同时保留 MPL 2.0 与所含 Apache 代码的许可声明。 | 可按版本和文件核对具体的复用痕迹。双方是否共同维持一套许可或协作安排，仍需独立证据。 |
| 技术传递 | 2012 年 LibreOffice 的一笔提交明确引用 Apache OpenOffice 的 SVG 修改。 | 可确认代码传递的方向和对象。SVG 在本研究的 Writer ODT 读写范围之外。 |
| 接口连续性 | 四组近同期发行版都登记同样的 ODT 扩展名、MIME 类型与读写入口。LibreOffice 的检测组件在所查版本间发生变化。另有一次跨软件演示和一份用户文档的打开记录。 | 共同配置和个别使用有证据。复杂样式、表格和修订记录在两个方向上的一般保留率未测。 |
| 组织关系 | 试编码发现邀请、引用和单向采用的材料。严格口径要求双方对同一 Writer ODT 事项有可核查的协作行为，且有分叉前后同口径的档案覆盖。 | 维护关系的变化方向不明。贡献者曾在两个项目出现，只能提供进一步查找同一事项的线索。 |
| 身份认同与相互承认 | 组织更名、邀请及标准讨论可以定位到事件。现有材料缺少同一批成员的纵向自述，以及两侧持续接纳或互认的行为记录。 | 成员认同和相互承认各记为不明。 |
| 资源与依赖 | 文档基金会公开了企业支持和咨询委员会的材料。 | 可以确认这一支持渠道。共同管理资源及两边对彼此的依赖程度尚无法估计。 |

以上逐项记录可按[证据索引](evidence.md)复核。

## 可以解释到哪一步

最稳妥的发现是**治理分开与部分接口继续可用同时存在**。这已经能区分两条轨迹，但档案间隔不足以估计它们变化的快慢。两条线路继承了共同的代码和格式入口，沿用旧配置本身就能解释一部分结果。共同的 ODF 标准及第三方测试活动也可能有作用。2014 年的一次演示提供了运行层线索，现有材料无法区分这些因素各自的影响。2015 年海牙联测报告列出 LibreOffice 测试版本，未列出 Apache OpenOffice，因此那次活动没有计入双项目运行证据。[配置对照与联测记录](evidence.md)

V0.4.3 的连接状态向量帮助把四个问题拆开：接口有没有继续用，维护者有没有继续合作，成员怎样理解归属，双方有没有实际互认。它也暴露出一个材料问题：分叉前只找到一个项目的技术基线，原有维护关系尚未可靠映射到后来的两个项目。若把缺失填成零，便会凭空得到一次组织断裂。这项回顾性研究尚无足够的基准和对照检验 H9 的方向。[V0.4.3 的 H9](../../docs/v0.4.3.md#119-分叉后的社会关系) · [Writer 分叉试编码](../../case-studies/writer-fork-pilot.md)

## 可复核的后续工作

复现实验可先固定一对历史版本、ODF 保存设置和三类可公开分享的 ODT 文件，分别检查基础段落、表格与样式、修订记录。两边各自起始，记录打开、保存和往返后的具体变化。研究维护关系时，先从分叉前的共同补丁和审阅建立可核验的基准配对，再以同一 Writer ODT 议题或补丁为线索查找两侧的后续行动。两项结果各自归档，读者可以单独核查其中任何一项。
